# SQL Function Documentation Generation

- Status: active
- Owner: DanRoscigno
- Last Updated: 2026-07-29

## Summary

Make the source the source of truth for SQL function reference documentation, so
that changing a function and changing its docs happen in the same file, and the
Markdown is regenerated mechanically rather than maintained by hand in three
languages.

This is a proof of concept covering 12 of 409 built-in function names. It is
modelled on the auto-documentation work in ClickHouse
([PR #49222](https://github.com/ClickHouse/ClickHouse/pull/49222) and what grew
from it), adapted to a codebase with a very different shape.

### Why the ClickHouse design does not port directly

ClickHouse hangs a `FunctionDocumentation` struct on each function's C++
registration call and exposes it through `system.functions`; a nightly job
queries a live server and splices the result into the docs.

StarRocks has no per-function registration site for scalar functions. All 993
scalar signatures live in a Python table, `gensrc/script/functions.py`, from
which `gen_functions.py` generates both the FE Java registry
(`VectorizedBuiltinFunctions.java`) and the BE `.inc` dispatch tables. That
table is the nearest equivalent to a registration site, so the documentation
payload belongs there.

The useful consequence: **the generator needs no running cluster.** It reads a
Python table. That removes the nightly-job machinery ClickHouse needs, and lets
the CI guard be a straight "re-run the generator and assert nothing changed".

### Shape

```
gensrc/script/functions.py           function_docs{}  <- the payload
        |
        v
gensrc/script/gen_function_docs.py   renders per-section blocks
        |
        v
docs/{en,zh,ja}/sql-reference/sql-functions/<category>/<name>.md
        {/* AUTOGENERATED_START:syntax */} ... {/* AUTOGENERATED_END:syntax */}
        |
        v
docs/scripts/check_autogenerated_regions.py   CI guard
```

## Decisions

**Payload is keyed by function name, not by signature.** `bitand` is five
signatures but one doc page; `reverse` is eighteen spanning both the string
(`30160`) and array (`150130+`) id ranges. A per-signature payload would
duplicate every paragraph five to eighteen times. Category is therefore a
declared field, not inferred from the id range.

**Markers are MDX comments, not HTML comments.** Docusaurus parses these `.md`
pages as MDX, where `<!-- ... -->` is invalid.
`docs/styles/local/HTMLComment.yml` enforces this at error level and
`ci-vale.yml` gates docs PRs on it. The first attempt used HTML comments and
produced 198 Vale errors.

**Markers are per-section, not per-page.** Hand-written sections are
interleaved with generated ones (`## Usage notes` sits between `## Return
value` and `## Examples`), and the interleaving differs per page and per
language. A single whole-page region would swallow hand-written prose.

**English is fully generated; zh and ja get the language-neutral sections
only** — syntax and examples, under localized headings. Argument and
return-value prose stays with the translation workflow. Generating English
alone would widen the drift `docs/scripts/sql_sample_parity.py` already
measures; generating prose would demand Chinese and Japanese from the developer
adding a function.

**Example captions on localized pages are preserved, never replaced.** A
caption is prose. The generator reuses whatever translated caption the page
already carries and regenerates only the query and result table around it. Where
a localized page has no caption for an example, that is reported for a
translator rather than filled in with English.

## Findings

Work on the 12 functions surfaced defects that generation prevents structurally:

- **`bit_shift_right.md` and `bit_shift_right_logical.md` had swapped
  contents** in `en` and `ja` — H1, prose, syntax and examples on each page
  described the other function. `zh` was correct. A reader following the
  `bit_shift_right` link got the logical-shift page.
- The two English pages carried **byte-identical `description` frontmatter**,
  so search snippets could not tell them apart.
- `bit_shift_right`'s parameter list contained the sentence *"The supported data
  type is BIGINT."* twice.
- One example's ASCII result table was malformed (47-character border over a
  45-character header).
- Japanese headings were **split within one seven-page category**: four pages
  used `## Syntax` / `## Parameters`, three used `## 構文` / `## パラメータ`.
- Three Japanese pages linked to `[Examples](#examples)`; one of those anchors
  was already dangling before any of this work.
- `en/locate.md` documents `SELECT LOCATE(...)` producing a lowercase
  `locate(...)` column header, while `en/reverse.md` documents uppercase
  `REVERSE(...)` producing an uppercase header. Both cannot be right.
  **Settled against 4.1.1: StarRocks always lowercases the function name in the
  column header, whatever case is typed.** `locate.md` was correct;
  `en/reverse.md` has been publishing a header StarRocks never emits.
- `en/reverse.md`'s array example claimed the header `reverse([4,1,5,8])`.
  StarRocks normalizes spacing inside the array literal and prints
  `reverse([4, 1, 5, 8])`. Found only by running it.

Verification also cleared two suspicions that turned out to be unfounded:
`cast('-2' AS INTEGER(32))` does parse and returns `2147483647`, so the original
spelling was valid (it was normalized to `CAST('-2' AS INT)` anyway, for
readability); and `lpad('hi', 5)` really does print the defaulted third argument
in its header as `lpad('hi', 5, ' ')`.

Separately, enabling the checker over `en/string-functions` surfaced one
pre-existing failure in `string_agg.md` — `SELECT STRING_AGG(name, ',' ORDER BY
name)` is documented but not accepted by the parser. That page is outside this
work and was left alone; it is a candidate for the `sql-doc-autofix` skill.

The swap, the identical descriptions and the duplicated sentence were fixed by
hand as a prerequisite; the rest fall out of generation.

## Acceptance Criteria

- [x] Payload validates; every documented name has a signature in
      `vectorized_functions` and a page in all three languages.
- [x] The payload is inert with respect to the build: `gen_functions.py` output
      is byte-identical across all 26 generated FE Java and BE `.inc` files.
- [x] Generation is idempotent — a second run is a no-op.
- [x] Nothing outside the markers changes; no prose is silently dropped.
- [x] Vale passes on all 36 touched pages (`0 errors`).
- [x] Generator unit tests pass (46 tests).
- [x] The CI guard passes on a clean tree and fails on a hand edit inside a
      region.
- [x] Cross-language parity does not regress; `split.md`'s zh gap closed.
- [x] `run_sql_samples.py` passes against a live cluster for the regenerated
      examples. Run against StarRocks 4.1.1 on 2026-07-31: `bit-functions`
      `PASS=16` and `string-functions` `PASS=19` in each of en, zh and ja. Every
      example value and column header was additionally confirmed by direct
      query.

## Side effect: doc-rot coverage

The generator emits queries in ```sql fences and results in ```plaintext
fences, dropping the `MySQL > ` client prompts. `extract_sql_samples.py`
harvests only ```sql fences, so these examples were previously invisible to the
doc-rot checker.

Across the 36 touched pages: **4 ```sql fences before, 126 after.** In
`en/bit-functions` alone the checker's plan goes from nothing extractable to
`RUN=16`.

Be precise about what that buys. `run_sql_samples.py` executes each statement
and drains the result set, but never compares the printed table to what the page
claims. A `PASS` means *the statement executed*. So CI will now catch a renamed
function or a changed signature in these examples, and will never catch a wrong
result value.

That is exactly why the payload was verified against a live cluster rather than
trusted: the printed outputs are the part no automation checks. Doing so found
two published errors in `en/reverse.md` that no amount of CI would have caught
(see Findings).

## Out of Scope

- **The queryable surface.** No `SHOW FUNCTIONS` columns and no
  `information_schema`. `information_schema.routines` is a stub — it maps to
  `TSchemaTableType.SCH_PROCEDURES`, which has no BE scanner, so it returns
  nothing. A real table needs a thrift enum, an FE system table and new C++.
  Adding description/syntax columns to `SHOW FULL BUILTIN FUNCTIONS` is FE-only
  and is the natural next step.
- **Aggregate and table functions**, registered in hand-written Java
  (`FunctionSet.initAggregateBuiltins()`, `TableFunction.initBuiltins()`). They
  need a builder-style payload that produces the same dict.
- **The other 397 function names.**
- **Frontmatter.** The generator reports when a page's `description` disagrees
  with the payload but does not write it; `docs/AGENTS.md` forbids changing
  frontmatter unhinted.
- **"See also" heading normalization.** `zh` uses both `## 相关文档` and
  `## 相关参考`, `ja` both `## References` and `## 参考文献`. These are
  hand-written sections; picking a canonical form in a language I am not
  authoring is an editorial call for the translation owners.

## Open Question for Maintainers

`gensrc/script/functions.py` is currently pure machine-readable data on the
build path. This adds prose to it. The payload is provably inert with respect
to code generation, but a maintainer may still prefer a sibling
`function_docs.py`. That was rejected here because it reintroduces the problem
the project exists to solve — documentation living somewhere the developer is
not looking — but it is worth settling before scaling past 12 functions.

## Decision Log

- 2026-07-29: Payload keyed by name rather than by signature; category declared
  explicitly, because `reverse` spans two module id ranges.
- 2026-07-29: Switched region markers from HTML comments to MDX comments after
  `local.HTMLComment` produced 198 Vale errors.
- 2026-07-29: Guard re-runs the generator instead of diffing regions between
  refs, as ClickHouse does. Possible because generation needs no cluster;
  catches stale generation as well as hand edits, and needs no opt-out label.
- 2026-07-29: Localized example captions preserved rather than regenerated,
  after a first pass replaced Chinese captions with English.
- 2026-07-29: Dropped `"Use this function to shift numeric values."` from three
  pages, superseded by four specific per-example captions. Recorded here because
  it is the one piece of prose removed without a direct replacement.
- 2026-07-31: Verified the whole payload against StarRocks 4.1.1. Two published
  claims in `en/reverse.md` were wrong (column-header casing, and spacing inside
  an array literal); the payload now reflects what the server prints. This is
  the argument for verifying rather than transcribing — both errors sit in
  example *output*, which no checker in the repo inspects.
