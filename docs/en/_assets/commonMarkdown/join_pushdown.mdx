## Join pushdown

From v4.2 onwards, the system can push multi-table joins (both `INNER JOIN` and `CROSS JOIN`) down to the external database when all joined tables come from the same JDBC catalog. This lets the source database execute the join using its own indexes and optimizer, and returns only the joined result back to the system.

### Enable join pushdown

Join pushdown is disabled by default. Set the session variable `enable_jdbc_join_push_down` to `true` to opt in:

```SQL
SET enable_jdbc_join_push_down = true;
```

### How it works

When the rule fires, the optimizer rewrites the local join over multiple JDBC scans into a single JDBC scan that issues one SQL query containing a JOIN against the remote database.

For example, the following query against two MySQL tables in the same JDBC catalog:

```SQL
SELECT o.order_id, c.region, o.amount
FROM jdbc0.db.orders o
JOIN jdbc0.db.customers c ON o.customer_id = c.customer_id
WHERE o.amount >= 20 AND c.region IN ('east', 'west');
```

Without pushdown, the system issues two separate scans and joins the result locally. With `enable_jdbc_join_push_down = true`, the whole join subtree is pushed down to the remote database. The local plan contains only one JDBC scan node, and the pushed-down SQL looks similar to:

```SQL
SELECT `c1`, `c2`, `c3` FROM (
    SELECT t0.`order_id` AS c1, t1.`region` AS c2, t0.`amount` AS c3
    FROM (SELECT `order_id`, `customer_id`, `amount` FROM `db`.`orders` WHERE `amount` >= 20) t0
    INNER JOIN (SELECT `region`, `customer_id` FROM `db`.`customers` WHERE `region` IN ('east', 'west')) t1
      ON t0.`customer_id` = t1.`customer_id`
) sr_merged;
```

Use `EXPLAIN` on a query to verify whether the join was pushed down.

### Scope and limitations

- **Join type**: `INNER JOIN` and `CROSS JOIN` are eligible for pushdown. Outer, semi, and anti joins fall back to local execution.
- **Same catalog**: all tables in a merged group must belong to the same JDBC catalog (same JDBC URI, credentials, and driver). Joins that mix two JDBC catalogs, or that mix JDBC tables with native tables, run locally.
- **Cross-table predicate required**: a group is pushed down only if it has at least one predicate that joins two tables in the group. Otherwise the rule skips it to avoid sending a pure cartesian product to the remote database.
- **All-or-nothing predicate pushdown**: every predicate owned by a group must be fully translatable to the remote dialect. If any predicate cannot be pushed (for example, a StarRocks-only function), the whole group falls back to a local join.
- **Statistics**: the merged JDBC scan reuses the same default statistics as a single-table JDBC scan. Downstream operators see the joined result as if it were one table of default size, and cardinality is not estimated from the underlying tables.
