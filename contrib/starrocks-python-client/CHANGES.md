Version history
===============

**Unreleased**

- Upgrading from 1.3.x:
  - `primary_key=True` columns with no `starrocks_*_key` give no key clause by default, so StarRocks makes a DUPLICATE KEY table, as in 1.3, with no warning. `create_engine(..., starrocks_infer_primary_key=True)`, `sqlalchemy.starrocks_infer_primary_key = true` for `engine_from_config()`, or `?starrocks_infer_primary_key=true` in the URL makes such a table a PRIMARY KEY table where StarRocks can hold one. Alembic's offline mode reads neither the URL's query string nor the engine options, so give the option in `context.configure(dialect_opts=...)` there too. A PRIMARY KEY table replaces a row whose key it already holds, refuses NULL keys, and can't alter its key columns later (StarRocks takes only a wider VARCHAR from 4.1.1 and a new comment from 4.1.3), so with the option on, one migration history can run on a database built before and fail on one built after. Autogenerate leaves existing DUPLICATE KEY tables alone, and with the option off leaves every table's key alone.
  - With the option on, StarRocks holds a PRIMARY KEY table when its key columns come first, in key order, are BOOLEAN, integer, DATE, DATETIME or VARCHAR columns, none of them generated or nullable, and fit the 128 bytes StarRocks loads in a row's key (a `VARCHAR(n)` counts n, and 2 more when another key column follows; an AUTO_INCREMENT column counts as BIGINT). The table must be distributed by HASH of key columns or by default, partitioned by key columns only, sorted by columns of those types or STRING, and free of the properties StarRocks refuses for a PRIMARY KEY table. Otherwise the dialect warns, naming the reason and what to change: key columns that don't lead go first (on SQLAlchemy 2.0, `mapped_column(sort_order=...)` for a mixin's columns), other keys can be named with `starrocks_duplicate_key`, and the warning quotes the `warnings.filterwarnings()` call that silences it. A table of another engine gets no key clause and no warning.
  - A DUPLICATE KEY table reflects no primary key, so `automap_base()` no longer maps it. A reflected ORM class needs `Column(..., primary_key=True)` or `__mapper_args__ = {"primary_key": [...]}`.
  - Secondary indexes now reflect, so autogenerate compares them: it writes `op.drop_index` for each index in the database that the model doesn't declare, where 1.3 never saw one. Declare the indexes your database has, or the next revision drops them.
  - Write `%` once in DDL text: view and materialized view definitions, `starrocks_partition_by`, `starrocks_distributed_by`, `starrocks_order_by`, `starrocks_refresh`, `starrocks_properties` and the `op.alter_*` operations. 1.3 raised on a single `%`, so a `%%` written for it now reaches StarRocks as `%%`, and the dialect warns about it. The warning names the filter that silences it for a `%%` you mean.
  - Offline SQL (`--sql`) needs `dialect_opts={"paramstyle": "named"}` in `run_migrations_offline()`, as Alembic's `env.py` template has, or each `%` in DDL text is written doubled.
  - `ALTER TABLE`, `CREATE INDEX` and `DROP INDEX` compiled from a construct now wait for the table's running schema-change jobs, and the two index statements for the index's own job, for at most `starrocks_schema_change_timeout` seconds (default 300), and then raise `SchemaChangeTimeoutError`. An `ALTER TABLE` with no job running first sends three `SHOW ALTER TABLE` queries, and a `CREATE INDEX` returns only when the index is built, where 1.3 returned at once, so on a large table `create_all()` or `op.create_index` now blocks for the build. `create_engine(..., starrocks_wait_for_schema_change=False)` restores 1.3's behaviour.
  - Connections report `AUTOCOMMIT`, where they reported `REPEATABLE READ`. Each new connection starts in it whatever the driver's autocommit setting, so a URL's `autocommit=false`, `connect_args={"autocommit": False}`, and `creator` and `async_creator` connections run as `AUTOCOMMIT`, as in 1.3. `isolation_level="READ COMMITTED"` runs DML in StarRocks transactions, so it needs StarRocks 3.5 or later, and `enable_sql_transaction` on where StarRocks has it, from 4.0.7 and 4.1.0. `READ UNCOMMITTED`, `REPEATABLE READ` and `SERIALIZABLE` are deprecated: they run as `AUTOCOMMIT`, as before, with a `FutureWarning` that names the line giving the level. Given to an engine, through `create_engine(isolation_level=...)`, `create_engine(execution_options=...)` or `engine.execution_options()`, it warns once, when the engine is made; given to `connection.execution_options()`, it warns at each call.
  - A `BEGIN` or `START TRANSACTION` sent as text raises `InvalidRequestError` where StarRocks would ignore it: before 3.5, and from 4.0.7 in a session whose `enable_sql_transaction` is off.
  - DOUBLE values read as `float` (1.3 returned `Decimal`), LARGEINT as `int`, MAP and STRUCT values as Python objects even where their text isn't JSON, and ARRAY<JSON> elements as JSON values (1.3 returned the server's text).
  - `func.array_agg()` results, and values read as the generic `sa.ARRAY`, are Python lists with typed elements, where 1.3 returned the server's text, such as `'[1,2]'`. Code that ran `json.loads` on them gets `TypeError`.
  - An ARRAY, MAP or STRUCT value that doesn't match its declared type, such as `ARRAY(INTEGER())` over `["a","b"]`, raises `ValueError` and fails the fetch, where 1.3 returned the server's text. Declare the type the server has. Through a CAST the dialect leaves out, array text that StarRocks' cast reads but that isn't JSON, such as `[a,b]`, is returned as the text, as 1.3 returned it.
  - A `cast()` to ARRAY, MAP or STRUCT is sent only where StarRocks can run it. One the dialect leaves out warns where StarRocks computes on the operand, as 1.3 warned of every such CAST, and a column of the result doesn't warn. The message is "The CAST to ... is left out, ...", so a filter for 1.3's "Datatype ... does not support CAST" no longer matches it.
  - A BOOLEAN inside an ARRAY, MAP or STRUCT reads only from 1, 0, `true` or `false`, or their text in any case. Any other value raises `ValueError`, where Python's `bool()` would read `"false"` as True.
  - `cast(<JSON>, String)` returns the JSON text, as SQLAlchemy documents it: a JSON string keeps its quotes, `'"s"'`, and a JSON null reads `'null'`. 1.3's CAST read `'s'` and SQL NULL. `cast(<JSON>, String(n))` renders `json_string(...)` and drops the length, where 1.3 sent `CAST(... AS CHAR(n))`.
  - A CAST to a float type is sent, where 1.3 left it out. The generic `sa.Float` with no precision, and a float type with a precision above 24, such as `Float(53)`, cast to DOUBLE, as MySQL reads `FLOAT(p)`. `FLOAT()`, `FLOAT(24)` or below, `mysql.FLOAT(M, D)` and REAL cast to StarRocks' 4-byte FLOAT, which keeps about 7 significant digits. Columns of these types are still created as FLOAT. A float element of a CAST to ARRAY, MAP or STRUCT follows the same rule, and a type with a StarRocks variant from `with_variant()` casts as the variant.
  - `ColumnAggType.COUNT` is removed, so code that names it gets `AttributeError`. StarRocks has no COUNT aggregate type, so no table could use it.
  - Autogenerate now writes a DROP and a CREATE for a materialized view whose definition changed, where 1.3 raised, and for a view that reads a column or object the revision removes. StarRocks drops the object's grants with it, and a materialized view's data until its refresh runs, so read such a revision before applying it.
  - A PROPERTIES value of `None` raises `CompileError`, where 1.3 sent the string `"None"`, and `cast(x, sa.Integer)` is `CAST(x AS BIGINT)`, where 1.3 sent `SIGNED INTEGER`.
  - `ViewSecurityType.DEFINER` is deprecated. StarRocks has no `SECURITY DEFINER`, so a view given it raises `CompileError`.
  - The `test` extra installs SQLAlchemy below 2.1 (2.1 is untested), and the tests need SQLAlchemy 1.4.47 or later, or 2.0.21 or later. The runtime dependency is unchanged, and the dialect imports and connects on every SQLAlchemy 1.4 release.
  - JSON scalars are stored as JSON scalars: a bound `5`, `True` or `None` is stored as a JSON number, boolean or null, where 1.3 stored the strings `"5"`, `"true"` and `"null"`. Rows 1.3 wrote still read as text, so one column can return both, and `col == 5` doesn't match the old rows.
  - PROPERTIES keys and values are escaped by the dialect, so a value escaped by hand for 1.3, such as a doubled backslash, is now escaped twice. Write each value as StarRocks should store it.
- Tests: every test runs in one `pytest` run under SQLAlchemy's testing plugin, in parallel, together with SQLAlchemy's and Alembic's dialect suites (Alembic's on SQLAlchemy 2.0 only). Worker databases, and the databases the tests create, are dropped with `FORCE`. Collection fails for a test the plugin would drop without a word: a module-level function; a misnamed, classmethod, staticmethod or non-function test, or one that a decorator without `functools.wraps` renames; a class with tests, nested or not, that the plugin doesn't collect; and a class that inherits `__test__ = False`. It also fails on SQLAlchemy 2.0 for a test under a mark with a return annotation, or a parameter annotation outside builtins, which SQLAlchemy 1.4 can't import. The test URL turns `starrocks_infer_primary_key` on, which SQLAlchemy's and Alembic's suites need; a `--dburi` that gives the option keeps its value. The asyncmy-only tests run with `--dbdriver asyncmy`. SQLAlchemy's ARRAY round trip runs, and its two literal round trips are skipped, since StarRocks refuses an ARRAY as a table's first column. Tested on StarRocks 3.3.22, 3.5.21 and 4.1.6, SQLAlchemy 2.0 and 1.4, and Alembic 1.14.1 to 1.20 (by @rad-pat)
- Queries and DML:
  - An executemany of ARRAY, MAP and STRUCT values works, as multi-row INSERTs, where 1.3 failed. JSON keeps one multi-row INSERT now that it binds through an expression. An executemany of a VARIANT column, or of SQL expressions in VALUES, goes as multi-row INSERTs instead of one INSERT per row. ORM flushes and Alembic's `bulk_insert` are included.
  - An INSERT executemany of more than 10,000 rows is split into INSERTs of at most 10,000 rows, which StarRocks requires. INSERT text whose VALUES hold more than placeholders is still sent by the driver, one row at a time.
  - `insert(...).with_dialect_options(starrocks_overwrite=True)` sends `INSERT OVERWRITE`, and `starrocks_label=` sends `INSERT ... WITH LABEL`. The label must be 1 to 128 ASCII letters, digits, `_` or `-`, as StarRocks requires, and any other label raises `CompileError`, including one with a backquote, which StarRocks would record under another name. An executemany of either goes as one INSERT, and raises when its rows need more than one, or when the driver would send it one row at a time.
  - A multi-table UPDATE renders as `UPDATE ... FROM`, and a multi-table DELETE with `USING`. `starrocks_limit` is refused on UPDATE and DELETE.
  - An OFFSET without LIMIT gets the LIMIT StarRocks needs, and `func.sysdate(n)` keeps its precision.
  - A CAST names the integer type asked for, with `sa.Integer` as BIGINT and unsigned types widened to a signed type. A CAST to Boolean works on SQLAlchemy 1.4, where it raised `AttributeError`. REAL compiles as FLOAT (by @rad-pat)
- JSON:
  - Index and path access render with `json_query` and the `get_json_*` functions; StarRocks has no `JSON_EXTRACT`. A chain of accesses compiles to one `json_query` or `get_json_*` call.
  - A key holding `\` is named exactly, and a key no StarRocks path can name raises.
  - `as_numeric(p, s)` reads the value's text, so it keeps every digit StarRocks stores, integers past 2**53 included. StarRocks stores a JSON number with a fraction, in an object or an array, as a DOUBLE, so the digits past a double's precision are lost at INSERT. JSON scalars round-trip as scalars.
  - Known issue: from StarRocks 4.0, Flat JSON stores a JSON null as `{}` when it shares an INSERT, or later a compaction, with JSON objects (StarRocks issue 81490). `"flat_json.enable" = "false"` keeps the null (by @rad-pat)
- Types:
  - `PERCENTILE` compiles. `PERCENTILE_UNION` and the agg-state aggregate types are accepted, and `ColumnAggType.COUNT`, which StarRocks doesn't have, is removed.
  - BINARY and VARBINARY keep their lengths. `Text` compiles as STRING, `sa.Enum` as a VARCHAR that holds its longest value, and NCHAR or a collated CHAR as CHAR. `TIMESTAMP`, which StarRocks doesn't have, compiles as DATETIME, and a DATETIME or TIMESTAMP precision is left out, since StarRocks' DATETIME takes none.
  - A `REAL` column is created as FLOAT, since StarRocks has no REAL. Autogenerate takes a model's STRING, `Text` or `UnicodeText` as equal to a reflected `VARCHAR(65533)`, and BINARY, VARBINARY and `LargeBinary` as one family, so it no longer reports them as changed.
  - STRUCT field names are quoted with the identifier preparer, and a field name holding a backquote raises. STRUCT columns that StarRocks 4.1 shows with backquoted field names reflect as STRUCT.
  - An aware datetime renders as its wall time in a literal, and on SQLAlchemy 1.4 an aware datetime and a `date` render as DATETIME literals, where 1.3 raised `CompileError` (by @rad-pat)
- ARRAY, MAP and STRUCT:
  - Values bind element by element through each element's own type, so quotes, decimals, dates, binary, JSON, TypeDecorators, a TypeDecorator over an ARRAY, MAP or STRUCT inside another collection included, and nested values round-trip exactly on StarRocks 3.3 to 4.1. Where StarRocks writes nested binary raw (3.x, 4.0 before 4.0.10, and 4.1.0), non-UTF-8 bytes inside a MAP or STRUCT break the connection, and an ARRAY of binary is read as hex there. The generic `sa.ARRAY` is adapted, its `dimensions` and `as_tuple` included, so `as_tuple=True` reads tuples.
  - Array text such as `"[1,2,3]"` still binds. Text that isn't a JSON array goes through StarRocks' own cast, as before.
  - Values are read with `json` first, and with the dialect's own scanner for what isn't JSON. Each column's converters are built once, so the columns 1.3 decoded, such as ARRAY<STRUCT> and ARRAY<DOUBLE>, read faster than in 1.3. MAP<INT, VARCHAR> and ARRAY<JSON> values, which 1.3 returned as text, take longer, since they are now decoded.
  - A CAST to ARRAY, MAP or STRUCT is sent where StarRocks can run it: on an ARRAY, MAP or STRUCT, on NULL, and on JSON where the server casts JSON to the type. That is MAP from 3.4.3 and STRUCT from 3.5.0, and never to an ARRAY element, MAP value or STRUCT field of a DATE, DATETIME, DECIMAL or binary type. It is left out for text, which StarRocks casts to ARRAY as no JSON parser would, for an expression with no type, and for the JSON casts StarRocks lacks. Any other operand keeps the CAST. A left-out CAST is read from the operand's text, element by element as StarRocks' cast of JSON reads it, in a column of the result or a subquery column selected as it is. Anywhere else StarRocks computes on the operand's own type, and the dialect warns: in a comparison, ORDER BY, GROUP BY, DISTINCT, UNION, a function's argument, a subquery the query computes on, and INSERT or UPDATE values.
  - ARRAY, MAP and STRUCT values aren't hashable, as SQLAlchemy's ARRAY and JSON aren't, so a legacy `Query` of an entity and such a column reads its rows instead of raising `TypeError`.
  - `starrocks+asyncmy` binds binary values as `X'...'`. With `async_creator`, pass `conv=starrocks.asyncmy.hex_literal_conversions(...)`, or the bind raises a `TypeError` that says so (by @rad-pat)
- Views and materialized views:
  - `create_all` and `drop_all` handle the views and materialized views in a `MetaData`, creating each after what it reads, a `text()` definition included.
  - A `select()` definition is compiled for StarRocks. Comments are escaped. Comment and security changes are applied with `CREATE OR REPLACE VIEW` and `ALTER VIEW ... SET SECURITY`.
  - A `select()` definition compiles once, with no server version, so it leaves out, on every server, each CAST to ARRAY, MAP or STRUCT that some supported StarRocks can't run, and each one warns: the view's column then has the operand's type.
  - A materialized view with neither `starrocks_refresh` nor `starrocks_distributed_by` is StarRocks' synchronous materialized view. It is created as before, now with a logged warning, because reflection and autogenerate can't see it.
  - `CREATE OR REPLACE MATERIALIZED VIEW`, which StarRocks doesn't have, raises `CompileError`.
  - `REFRESH ASYNC` is sent for the `SCHEDULE` spelling, which StarRocks before 4.1.1 doesn't know (by @rad-pat)
- Tables and indexes:
  - `CREATE INDEX` follows StarRocks' grammar, with `starrocks_using`, `starrocks_properties` and `starrocks_comment`. The dialect waits for the index's build job, and logs a warning if StarRocks cancels it.
  - An index StarRocks can't build raises `CompileError` instead of reaching it: a unique, multi-column or expression index, `CREATE INDEX IF NOT EXISTS`, `DROP INDEX IF EXISTS`, an unknown `starrocks_using`, `starrocks_properties` without `starrocks_using`, and MySQL's `starrocks_length`, `starrocks_prefix` and `starrocks_with_parser`.
  - PROPERTIES keys and values are escaped, and a property whose value is `None` raises `CompileError`, where 1.3 sent `"None"`.
  - `starrocks_order_by` takes a list of column names, and quotes each bare name as StarRocks needs. An item holding a space, a parenthesis or a backquote is sent as written.
  - A PARTITION BY a column or a list of columns gets the parentheses StarRocks 3.3 needs.
  - Names StarRocks reserves and MySQL doesn't, such as `files`, `text` and `json`, are quoted.
  - `VARIANT` columns are refused before StarRocks 4.1, and view `starrocks_security` before 3.4.1 (by @rad-pat)
  - With `starrocks_infer_primary_key` on, a table with a `bucket_size` property and no `starrocks_distributed_by` stays a DUPLICATE KEY table, with the warning, since StarRocks 4.1 refuses the PRIMARY KEY table.
  - `Index(mysql_using=...)` raises `CompileError`, where it was dropped silently; use `starrocks_using`.
- Reflection:
  - Only PRIMARY, UNIQUE and AGGREGATE KEY tables report a primary key. A table is reflected once instead of twice, and on SQLAlchemy 2.0 information_schema is read once per schema.
  - Secondary indexes reflect from `SHOW INDEX`, with their type, properties and comment, and autogenerate compares them.
  - String defaults, AUTO_INCREMENT, PARTITION BY, and a materialized view's REFRESH and PROPERTIES are read from the clauses themselves, so neither a column or index comment nor a STRUCT field name can change them. That includes StarRocks 3.3's unescaped quotes in PRIMARY KEY comments and its bare STRUCT field names, and a multi-line comment with a line that starts with a column's name. A LIST partition value holding a quote, which StarRocks prints unescaped, can still run the reflected partition list on into the later clauses.
  - A partition named like a clause keyword, such as `p_texas` or `` `as` ``, no longer cuts the reflected PARTITION BY short. A materialized view's REFRESH, PROPERTIES and AS SELECT are found the same way, and a REFRESH clause the grammar can't read keeps its `ASYNC`.
  - A RANGE partition expression whose string holds a parenthesis, such as `str2date(s, '(%Y-%m-%d')`, reflects whole, and a partition clause that can't be read raises `SQLParseError` instead of a `TypeError`.
  - A materialized view's `partition_retention_condition`, its query-rewrite properties and its `session.*` properties are read from its DDL, since StarRocks leaves them out of information_schema, so autogenerate no longer alters them on every run.
  - Views and materialized views can be inspected through an `Engine`. A materialized view's columns reflect in SELECT order, and its definition without a trailing `;`.
  - StarRocks 3.5's generated partition column is left out, and its expression put back into the partition clause (by @rad-pat)
  - A materialized view whose property value holds an unpaired quote, as StarRocks 4.1 prints `city != "O'Brien"`, reflects with its whole definition. Its `excluded_refresh_tables`, `resource_group`, `unique_constraints` and `foreign_key_constraints` are read from its DDL too, the two constraint properties without the catalog and database StarRocks prints.
- Autogenerate:
  - A change StarRocks can't ALTER is skipped with a warning, and the rest of the revision is generated. That covers a key type, a partition method, a column default, and the table and materialized view properties StarRocks refuses to SET.
  - A table attribute the model leaves out, such as DISTRIBUTED BY or ORDER BY, is left as the database has it, where 1.3 raised `NotImplementedError` asking for it.
  - Unique constraints and foreign keys, which StarRocks tables can't hold, are left out of the comparison, so the same `create_unique_constraint` or `create_foreign_key` is no longer proposed on every run.
  - A materialized view whose definition changed is dropped and created again, where 1.3 raised `NotImplementedError`. The new one keeps the database's refresh when the model states none, and the properties the model leaves out unless they hold StarRocks' default. It leaves out the properties CREATE refuses for it, and the warning names each one: `auto_refresh_partitions_limit` and the `partition_*` properties for an MV with no PARTITION BY, `auto_refresh_partitions_limit` for a MANUAL one, `excluded_trigger_tables` and `excluded_refresh_tables` for one not refreshed ASYNC, `partition_ttl_number` from StarRocks 3.4.1 when its partitions are not known to be RANGE ones, the entries of `excluded_trigger_tables` and `excluded_refresh_tables` that its new definition doesn't read, and a `partition_retention_condition` that names a column it no longer has.
  - Before StarRocks 4.0.2 for a materialized view, and 4.0.7 for a view, a definition that can't be compared through a temporary view counts as changed only when the change is certain: only the model's definition fails to go through the temporary view, as when it reads a column the revision adds; it reads what the revision creates; or the database's reads a table, view, materialized view or column that the revision drops without creating it again, or renames. For a view, the materialized views the revision drops count too. Otherwise autogenerate warns and generates no operation for it.
  - A `%` in a view or materialized view definition, as in `date_format(dt, '%Y-%m')` or `LIKE 'x%'`, no longer stops the temporary-view comparison, which altered such views on every run before StarRocks 4.0.7.
  - A view or materialized view whose column list names repeated SELECT names, as `SELECT t.id, t2.id` under `(id1, id2)`, is compared through a temporary view that states the column list too. Before StarRocks 4.0.7 (views) and 4.0.2 (materialized views), a change to such a definition was only warned about, even for a user with every privilege.
  - The warning that a definition could not be compared quotes the error StarRocks gave the temporary view. It advises granting CREATE VIEW, SELECT and DROP only for access denied, an unknown database, or a temporary view the user cannot see. A temporary view that was never created is no longer dropped, so a missing `starrocks_temp_view_schema` no longer logs a drop failure for each definition.
  - A change inside a string literal of a definition, such as `'Active'` to `'ACTIVE'`, is detected, and so is a changed decimal number when the definitions are compared as text.
  - View and materialized view operations are ordered by what each reads, so both directions of a revision run.
  - A view whose old definition reads what the revision removes, a table, view or materialized view it drops or renames, or a column it drops or renames, is dropped before the table operations and created again after them, so the downgrade runs. StarRocks drops a view's grants with the view, so autogenerate warns when it does this, naming the views. A view that reads none of it, such as one over a table that loses only a column the view doesn't read, is altered in place after the table operations and keeps its grants.
  - Differences that are only spelling are no longer reported: function and quoted-literal defaults, `time_slice` partitions, an omitted MV refresh moment, `bloom_filter_columns` order, index names that differ only in case, and the `dynamic_partition.start`, `start_day_of_week`, `start_day_of_month`, `enable` and `prefix` that StarRocks adds.
  - On SQLAlchemy 1.4, autogenerate compares tables, and leaves the database's views and materialized views alone with a warning (by @rad-pat)
  - A restated `func.now()` or `CURRENT_TIMESTAMP` default, which StarRocks reflects alike, and a BOOLEAN `'true'` StarRocks keeps as `'1'`, no longer log a DEFAULT change on every run.
  - `excluded_trigger_tables` and `excluded_refresh_tables` compare in any order and spacing.
  - A downgrade never turns dynamic partitioning on: on a table with no `dynamic_partition.*` property it sets `dynamic_partition.enable` back to `false`.
  - The type, comment and properties an index declares (`starrocks_using`, `starrocks_comment`, `starrocks_properties`) are compared, and an index that differs is dropped and created again. An option the model leaves out is left alone.
  - A change to the distribution of a RANDOM-distributed table is skipped with a warning, since StarRocks refuses to alter it.
  - A view comment that says ` SECURITY NONE` no longer reads as the view's security, and the warning for a definition that couldn't be compared advises only what would cure it.
- Alembic operations:
  - `op.alter_column` renames in an ALTER of its own, and restates KEY or the aggregate type in MODIFY COLUMN. It leaves an unchanged AUTO_INCREMENT out, and refuses a changed one. Offline, `autoincrement=False` leaves it out.
  - `op.alter_column` with a `server_default` and no `existing_server_default` compares it with the column's default in the database, as StarRocks keeps both, so restating an unchanged default for a type change works: `NULL` (`sa.null()`, `text("NULL")`) for a column with no default, and `"true"` or `"false"`, in any case, for a BOOLEAN default that StarRocks 3.5.11, 4.0.4 and 4.1.0 and later keep as `'1'` or `'0'`. A changed one raises. Offline it is sent as given.
  - `op.alter_table_properties` sends one SET per property group, and `op.alter_materialized_view` sends a refresh and properties as two statements. These and `op.alter_view` compile all their statements before running the first, so a security the server lacks, or a property with no value, changes nothing.
  - `op.alter_view` takes `starrocks_security=`, as `op.create_view` spells it, as well as `security=`.
  - `op.drop_index` matches names without regard to case, and skips only an index an earlier `drop_column` in the run took, under a `schema_translate_map` too, or a missing one with `if_exists=True`.
  - `combine_column_alters` combines a table's column adds before a change of its sort key or properties, and the drops after it, so such a table gets two statements. StarRocks refused a `bloom_filter_columns` SET after the combined drop. It does the same around a change of distribution that names an added or dropped column, since StarRocks refuses to drop a column the old distribution still names; a distribution change that names none, such as a new bucket count, keeps the column changes in one statement.
  - Constraint operations StarRocks can't run, and a column default change, raise.
  - `op.rename_table` sends `RENAME` without `TO`.
  - Offline literals of ARRAY, MAP and STRUCT values are exact (by @rad-pat)
  - Restating `server_default=func.now()` for a `DEFAULT now()` column is no longer refused: StarRocks reflects `now()` and `CURRENT_TIMESTAMP` alike, so they are taken as one default.
- Transactions and DDL execution:
  - With `isolation_level="READ COMMITTED"`, the first INSERT, UPDATE or DELETE opens a StarRocks transaction. COMMIT and ROLLBACK reach StarRocks. DDL commits first, and statements StarRocks refuses inside a transaction raise before they are sent.
  - Each `ALTER TABLE`, `CREATE INDEX` and `DROP INDEX` compiled from a construct that names its table (SQLAlchemy's index and table-comment statements, Alembic's operations and the dialect's own) waits for the table's running `COLUMN`, `OPTIMIZE` or `ROLLUP` job, for at most `starrocks_schema_change_timeout` seconds (default 300; `None` or `0` waits without a limit, and a negative value raises `ArgumentError`), and then raises `SchemaChangeTimeoutError`. After a `CREATE INDEX` or `DROP INDEX`, which has already run, a timeout of the wait for its own job only warns. Such a statement sent as text, through `exec_driver_sql()`, `text()`, `op.execute()` or SQLAlchemy's `DDL()`, doesn't wait. `starrocks_wait_for_schema_change=False` turns the wait off. Both are `create_engine()` options, which the URL's query string can also give. They are separate from the Alembic `context.configure()` options of the same names, which are off by default and wait after each of a migration's schema-change statements.
  - StarRocks shows a `ROLLUP` job as `FINISHED` up to about 60 ms before it frees the table. A statement it refuses in that gap with "A materialized view or rollup index is being created on the table", after the wait saw a `ROLLUP` job end, is sent again, after 50 ms and then after pauses that double up to a second, within `starrocks_schema_change_timeout`.
  - SQLAlchemy doesn't set a level given to `execution_options()` on the DBAPI connection that replaces one after a disconnect or `invalidate()`, and every new connection starts in `AUTOCOMMIT`. A Connection whose statements then run at another level than it was given gets an `SAWarning`, once.
  - Every statement's error is reported from a DDL construct that compiles to several statements, including over asyncmy and `async_fallback` (by @rad-pat)
  - `starrocks_schema_change_timeout` refuses `nan`, a negative number and text that isn't a number with `ArgumentError`.
- Autogenerate no longer resets a table or materialized view property the model omits back to a hardcoded default; it is left as the database has it. Many defaults depend on the StarRocks version or FE config (`replication_num`, `fast_schema_evolution`, `bucket_size`), so the reset was often spurious. To manage a property, declare it in the model (by @chris-celerdata)
